| 3 | Replaced the sort with a counting-sort scatter: each thread already pushes its presence/position entries in ascending `(doc_id)` / `(doc_id, position)` order (documents are scanned in file order, and thread ranges are themselves in ascending doc-id order), so concatenating thread 0's, then thread 1's, ... entries for a given term is ALREADY fully sorted -- no comparison sort needed at all, just sum each thread's per-term counts into a histogram, prefix-sum it into offsets, then copy (O(n), one linear pass) each thread's entries into their term's slot. `build_index` dropped 2.67s -> 0.80-0.87s; TOTAL dropped 3.0-3.1s -> 1.2-1.3s (~2.4x faster). Also swapped the term-lookup `HashMap`'s hasher from std's default (SipHash, DoS-resistant, unneeded here since the table is built from the query file's own terms) to a hand-rolled FNV-1a (`src/fnv_hasher.rs`, no new dependency) -- a small additional win (`scan_docs` 512ms -> ~470ms), small enough to show the per-byte tokenization loop itself, not the hashmap lookup, is `scan_docs`'s real floor. Hash-matched again on every dataset in step 1 after both changes, plus against the REAL official S3 seed-1 data and 4 holdout seed/scale combinations via `verify-official.yml` (19 jobs total for track b across both its matrices, all passed) -- the official seed-1 hash (`f8697...e80927`) matches the spec's own published SHA-256 exactly.
